## Key Decisions

### 1. History-writing commands request delivery through a kernel module, not the event store
Hooking `emitEvent` directly would have coupled the event store to the job queue; a periodic poll would have failed the plan's "triggering event causes a real job" exit criterion. `scheduleHistoryNotification` gives Cards/Wiki/Collaboration a one-line call without importing the Subscriptions context.

### 2. Notification delivery reads the same union projection the feed reads
`notify.server.ts` extends `historyEntriesAfter` (Phase 21's feed query) with an oldest-first cursor and `sourceId`/`pageIdentifier`, rather than building a second read path — a subscriber hears about exactly what the feed shows.

### 3. MQL subscription filters are re-parsed at delivery time, not stored compiled
A renamed property sets `last_error` on the subscription (surfaced, recoverable) instead of crashing the whole delivery batch; it clears automatically once the filter parses again.
