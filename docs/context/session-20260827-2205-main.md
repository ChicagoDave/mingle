## Key Decisions

### 1. History-writing commands request delivery through a kernel module, not the event store
Hooking `emitEvent` directly would have coupled the event store to the job queue; a periodic poll would have failed the plan's "triggering event causes a real job" exit criterion. `scheduleHistoryNotification` gives Cards/Wiki/Collaboration a one-line call without importing the Subscriptions context.

### 2. Notification delivery reads the same union projection the feed reads
`notify.server.ts` extends `historyEntriesAfter` (Phase 21's feed query) with an oldest-first cursor and `sourceId`/`pageIdentifier`, rather than building a second read path — a subscriber hears about exactly what the feed shows.

### 3. MQL subscription filters are re-parsed at delivery time, not stored compiled
A renamed property sets `last_error` on the subscription (surfaced, recoverable) instead of crashing the whole delivery batch; it clears automatically once the filter parses again.

### 4. ADR-0018 — background work is a transactional outbox drained in-process
Written after the Phase 22 commit at the user's confirmation: `docs/adrs/0018-background-work-is-a-transactional-outbox-drained-in-process.md` (ACCEPTED, 8 decisions) — jobs enqueued on the command's `tx`, dedupe-while-pending via partial unique index, at-least-once with quadratic backoff, one in-process worker from `entry.server.tsx`, kernel-module requests, env-built adapters behind domain-owned interfaces, notifications over the version trails with per-trail cursors, mail verified against a real SMTP server.

### 5. Tree relationship values are card numbers, not row ids
Legacy's `TreeRelationshipPropertyDefinition` stored the ancestor's database id. Numbers are the project-scoped stable identity everything user-facing already relies on (MQL, card links, snapshots), so storing the number lets `Release = 12` resolve with no join and keeps a `card_versions` snapshot self-describing without a lookup against a row that may since have changed identity.

### 6. Placement is structural, not a value write
A tree relationship's value changes only through `addCardToTree`/`removeCardFromTree`/`reconfigureTree`, which write the whole ancestry (or clear it) as one unit and revise affected descendants together. `canonicalPropertyValue` refuses a direct set of the kind — the invariant that ancestry stays internally consistent cannot be upheld by a single-property write, so the write path for the kind was closed off entirely rather than trusted to callers.

### 7. Tree card types are recorded explicitly, not inferred
Legacy inferred a tree's type chain and its leaf from relationship-property positions. `tree_card_types` stores the chain as its own rows, so the leaf (which carries no relationship) is a fact rather than something derived from "the last position with no relationship," and reconfiguration can change the chain without depending on position arithmetic staying accidentally correct.
