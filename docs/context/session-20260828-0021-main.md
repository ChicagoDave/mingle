- New `mingle-ts/app/domain/cards/aggregates.server.ts`: read-only engine computing every aggregate a holder card carries as one SQL statement each (COUNT, or SUM/AVG/MIN/MAX of descendant values), with `aggregateConditionErrors` pinning legacy `AggregateConditionValidations` plus a new rule — an aggregate condition may never reference another aggregate.

- Deliberate divergence pinned by a test: a holder's aggregate refresh appends **no** card version to the holder (legacy `bypass_versioning`) — the trail records edits, not a descendant's side effect.
- Readers wired: MQL treats an aggregate as a number family, transitions refuse it as action/prerequisite, card page renders read-only, tree page lists aggregates with a define form.

## Key Decisions

### 1. ADR-0019 — derived values on other cards recompute in the writing transaction
Written and ACCEPTED: `docs/adrs/0019-derived-values-on-other-cards-recompute-in-the-writing-transaction.md`. Synchronous in-transaction recomputation of derived values on OTHER cards, keyed off `appendPropertyValueChanges`; all inputs fixed at definition time; the holder's refresh appends no card version; formulas and aggregates share one materialization path with `properties.server.ts` as sole writer.

### 2. Aggregate is a property kind, not a new store
Same STI-to-discriminator move Phases 14/20/23 made for other property subtypes — keeps the value on `card_property_values`/`card_versions` rather than inventing parallel storage.

### 3. Mutation-hook boundary made single-purpose
Verification surfaced that the placement hook (`addCardToTree`) and the value-write hook (`appendPropertyValueChanges`) were both recomputing "after" holders unconditionally, masking two mutants. Fixed by giving each hook one reason to fire: the placement hook now recomputes only on first placement (the belonging row is what makes a card count), the value-write hook recomputes before/after holders on every value change.
