# Proposal: Project templates — Kanban

**Status**: DONE — 5/5 items delivered by `docs/work/archive/project-templates/plan.md` (2026-08-29, session ba5848); reviewed the same day, P-1's format decision extracted as ADR-0024 and ACCEPTED
**Origin**: conversation — the observation (2026-08-29, session ba5848) that legacy Mingle was a Scrum/Kanban PM system by virtue of its shipped project templates, and that the port rebuilt the card engine but not the templates: a new project is a bare shell with one card type.
**Date**: 2026-08-29
**Session**: ba5848

Legacy shipped three template specs in `mingle/templates/specs/` — `scrum_template.yml` (1,786 lines), `agile_template.yml`, `kanban_template.yml` — offered as "Pre-defined templates" on New Project (`_new_form.rhtml` → `ConfigurableTemplate#copy_into` → `ProjectCreator#merge!`). A spec carries card types, property definitions with ordered managed values, card defaults, project variables, trees, seed cards, tabs (a saved grid/list view promoted to a tab, with lanes and WIP limits), and wiki pages with macros. The port's configuration bundle (`app/domain/import-export/bundle.server.ts`, `mingle-project-template` v1) carries card types, properties, trees, aggregates, transitions and variables only — by design "no cards, versions, members, pages or history" — and `/projects/new` has no template step. Every engine feature a Kanban template leans on exists in the port except two: **card defaults** (no schema, no command) and **WIP limits** on grid lanes (no schema, no rendering). This proposal is scoped to **Kanban only**, with the columns **Proposed / Ready / Backlog / In Progress / In Test / Completed**; Scrum and Agile-hybrid are out of scope until this lands and can be proposed separately. Items are ordered by dependency: the format first, the two engine gaps next, then the template content, then the picker that exposes it. Reviewed 2026-08-29 (session ba5848): P-1 carried an unrecorded format decision, extracted as ADR-0024 and ACCEPTED in the same session; its Decisions 4–6 absorb the review's advisory notes (identity marker only, `{{template:today±N}}` substitution on import, content written through the existing card-import, page and favorites writers, defaults applied by `createCard`'s own property writer). All five items are ACCEPTED.

## Items

### P-1: Template bundle format carries pages, tabs, card defaults and seed cards
- **Done when**: `parseBundle` accepts `mingle-project-template` version 2 with four optional sections — `pages` (name + content), `favorites` (team favorites with style, filters/MQL, columns, lane property, `tabView`, and WIP limits per P-3), `cardDefaults` (per card type: default property values by name, with `(current user)` as a legal user value), and `cards` (name, type, number, description, property values by name) — still naming everything by name; `importProject` applies all four in one transaction after the v1 sections it already applies; `exportProject` writes them; a version-1 bundle still imports unchanged; and a behavior test exports a project carrying all four, imports it into a fresh project, and asserts on the created pages, favorites/tabs, defaults and cards row by row.
- **Status**: DONE (2026-08-29) — Phase 3 of `docs/work/archive/project-templates/plan.md`

### P-2: Card defaults per card type
- **Done when**: a card type carries default property values (`card_defaults`: property name → value, where a user property may hold the `(current user)` marker resolved to the actor at creation), edited on the card-type admin page and set through a domain command that emits `CardDefaultsSet`; `createCard` applies the defaults for every property the caller did not set explicitly, so a new card lands in the default lane rather than "(not set)"; API card creation inherits the same behavior; and behavior tests assert on the persisted `card_property_values` of a card created with and without an explicit value, on the resolved current-user default, and on the rejection of a default naming a value the property does not manage.
- **Status**: DONE (2026-08-29) — Phase 1 of `docs/work/archive/project-templates/plan.md`

### P-3: WIP limits on grid lanes
- **Done when**: a team favorite of grid style may carry a WIP limit per lane value (count only; legacy's sum-of-property variant is not carried), edited from the grid's lane header when the current view is a saved favorite and persisted through `app/domain/cards/favorites.server`; the lane header renders `n / limit` and gains an `over-limit` class when the lane holds more cards than the limit; a drop into a full lane is still allowed (legacy warned, it did not refuse); and behavior tests assert on the persisted limit, on the rendered header for an under- and an over-limit lane, and on the limit surviving the favorite round-trip through P-1.
- **Status**: DONE (2026-08-29) — Phase 2 of `docs/work/archive/project-templates/plan.md`

### P-4: The shipped Kanban template
- **Done when**: `mingle-ts/templates/kanban.json` is a P-1 bundle defining one card type `Work`; a managed `Status` property with values in this order — `Proposed`, `Ready`, `Backlog`, `In Progress`, `In Test`, `Completed`; `Owner` and `Pair` user properties; card defaults `Status = Proposed`, `Owner = (current user)`; a `Kanban Board` team favorite promoted to a tab — grid style, filtered to `[Type][is][Work]`, lanes by `Status` in column order, WIP limits on `In Progress` and `In Test`; four seed cards spread across the first columns as legacy's did; and an `Overview Page` whose cumulative-flow `daily-history-chart` has one series per column and whose start/end dates are written as `{{template:today±N}}` tokens resolved on import per ADR-0024 Decision 5 (legacy did this with ERB at copy time). A behavior test imports the file into a fresh project and asserts on every entity above, and the file is validated by `parseBundle` in the suite so a hand-edit that breaks it fails the gate.
- **Status**: DONE (2026-08-29) — Phase 4 of `docs/work/archive/project-templates/plan.md`

### P-5: Template picker on New Project
- **Done when**: `/projects/new` offers "Blank project" plus every template found in `mingle-ts/templates/*.json` (legacy's "Pre-defined templates" thumbnails, harvested from `_new_form.rhtml`/`_thumbnail.rhtml`), creating the project through `importProject` with the entered name and identifier when a template is chosen and through `createProject` otherwise; the resulting project's first tab is the template's tab and its overview page renders; and behavior tests cover both paths through the route's action, including the site-admin authorization that `createProject` already enforces.
- **Status**: DONE (2026-08-29) — Phase 5 of `docs/work/archive/project-templates/plan.md`
