# Session Plan: Project templates — Kanban (P-1..P-5)

**Created**: 2026-08-29
**Plan Status**: DONE (2026-08-29 — all 5 phases complete; P-1 through P-5 delivered)
**Overall scope**: Ship the Kanban project template end to end — the two missing engine features it needs (card defaults, WIP limits), the widened bundle format that carries pages/favorites/cardDefaults/cards, the shipped `mingle-ts/templates/kanban.json` file, and the New Project template picker that exposes it.
**Bounded contexts touched**: Card Management (`app/domain/cards`) — card defaults, WIP limits, grid rendering; Import/Export (`app/domain/import-export`) — bundle format v2, export/import, card-import reuse; Wiki & Content (`app/domain/pages`) — template-time token substitution on import; Projects (`app/routes/projects.new.tsx`) — template picker adapter.
**Key domain language**: card defaults, transition-only property, WIP limit, team favorite (tab), bundle (`mingle-project-template`), `includeContent`, `(current user)` marker, `{{template:today±N}}` token.

## References consulted
- `docs/adrs/0024-project-templates-are-versioned-bundles-carrying-optional-content-sections.md` — a template is a bundle (no second artifact); `BUNDLE_VERSION` moves to 2, backward-readable; `includeContent` defaults false; `(current user)` is the only identity marker, resolved at import; `{{template:today±N}}` is the one substitution, expanded once by the importer before storage; imported content must go through the existing writers (`importCards`, `favorites.server`, `createCard`'s own property writer) — and Decision/Consequence ordering requires P-2 and P-3 (engine features) before P-1's `cardDefaults`/WIP fields.
- `docs/adrs/0004-property-history-as-id-keyed-version-snapshots.md` — card version snapshots are keyed by property definition id, never name; any new version-appending write (card creation with defaults applied) must write the full id-keyed snapshot via the existing `cardPropertySnapshot`/`appendPropertyValueChanges` path, not a parallel one.
- `docs/adrs/0005-favorites-as-single-row-with-kind-discriminator.md` — favorites are one row with a `kind` discriminator and legacy-wire-form params; a new WIP-limit field is a column/JSON addition to the same row, not a second table; writes go only through `app/domain/cards/favorites.server.ts`.
- `docs/adrs/0008-applycardpropertyvalue-is-the-ui-property-change-entry-point.md` — any new caller that sets a property value must explicitly choose `setCardPropertyValue` vs `applyCardPropertyValue`; card creation with defaults is a new-card write (not a workflow gesture) so it uses the direct property writer, not the dispatcher — this is stated explicitly in Phase 1 below rather than left implicit.
- `docs/adrs/0009-transition-only-enforcement-is-split-between-guard-and-dispatcher.md` — a default naming a transition-only property's value is still a direct write at creation time (no drag gesture exists yet), so it is exempt from the dispatcher split, but the guard's role-sensitivity is irrelevant at creation (no prior value to bypass) — noted so Phase 1 does not accidentally route defaults through `applyCardPropertyValue`.
- `docs/adrs/0012-a-name-stored-in-text-is-a-reference-rename-rewrites-or-is-refused.md` — card defaults, WIP limits, and bundle sections all name properties/card types/lanes by NAME (never id) per existing bundle convention; this is consistent with ADR-0012's rule that human-authored/portable text holding a name is a reference, and constrains Phase 1–3 schema choices to store defaults and WIP limits keyed by name-resolvable ids the same way `property_definitions`/`favorites` already do (id in-DB, name at the bundle boundary) rather than inventing a third convention.
- `docs/adrs/0019-derived-values-on-other-cards-recompute-in-the-writing-transaction.md` — Card defaults must not become a second writer of `card_property_values`; Phase 1 applies defaults through `createCard`'s own transaction using the existing property-writer, consistent with "the aggregate engine is read-only; a session that finds itself writing `card_property_values` from anywhere else is breaking Decision 4" (generalized here to card creation, not just aggregates).
- `docs/context/project-profile.md` — standing gate is `cd mingle-ts && npm run verify` (typecheck, full behavior suite, build); behavior tests live at `mingle-ts/test/<feature>.behavior.test.ts` and assert on re-queried table state, never on return values or mocks; `documentationStandard: "always"` — every file touched needs a header comment and every public function a method header, retrofitted on files this plan edits.

## Phases

### Phase 1: Card defaults engine (Card Management)
- **Tier**: Medium
- **Budget**: 250
- **Domain focus**: Card Management — a new `card_defaults` concept on `PropertyDefinition`/`CardType`, applied at card creation. Emits `CardDefaultsSet`.
- **Entry state**: No `card_defaults` schema or command exists (grep confirms). `createCard` (`app/domain/cards/commands.server.ts`) creates a card with no property values set. Card-type admin lives in `app/routes/projects.settings.tsx`.
- **Deliverable**: Implements P-2.
  - New Drizzle table (migration via `drizzle-kit generate`, next file after `0025_schedules.sql`) holding, per card type × property definition, a default value in canonical stored form, with `(current user)` as a legal literal for user-kind properties only (validated at write time, resolved at read/apply time to the actor).
  - New command `setCardDefaults(db, { projectId, cardTypeId, defaults: {propertyName: value}, actorUserId })` in a new `app/domain/cards/card-defaults.server.ts`, authorizing at `PROJECT_ADMIN` (legacy card-type admin privilege), rejecting a default naming a value the property does not manage (enumerated) or a non-`(current user)` user literal, emitting `CardDefaultsSet`.
  - `createCard` (`app/domain/cards/commands.server.ts`) applies the card type's defaults, in the same transaction, for every property the caller did not set explicitly — writing through the existing property writer (`properties.server.ts`'s value-setting primitive, e.g. the same path `appendPropertyValueChanges`/`canonicalPropertyValue` use), never `applyCardPropertyValue` (ADR-0008: this is a new-card write, not a workflow gesture) and never a second `card_property_values` writer (ADR-0019). `(current user)` resolves to `input.actorUserId` at creation time.
  - API card creation (`app/routes/api.v1.projects.cards.ts`) inherits the behavior for free by calling the same `createCard`; confirm this in the phase (no separate code path to touch, but assert it in a test).
  - Card-type admin UI: extend `app/routes/projects.settings.tsx`'s existing card-type section with a defaults editor per card type (property → default value, `(current user)` option for user properties) — following the file's existing action-dispatch pattern (`defineCardType`/`definePropertyDefinition`/`setPropertyTransitionOnly` already live there).
  - Legacy files to harvest for behavior only (not code): `mingle/app/models/card_defaults.rb` (`update_properties`, `(current user)` handling is elsewhere in `PropertyValue`), `mingle/templates/specs/kanban_template.yml`'s `card_defaults:` block for the exact shape (`card_type_name` + `properties: {name: value}`).
  - Boundary Statement (rule 8a) required before editing `app/domain/cards/card-defaults.server.ts` and any change inside `properties.server.ts`/`commands.server.ts` (both under `app/domain/**`).
  - Behavior Statement (rule 12) required for `setCardDefaults` and for the modified `createCard`.
  - New test file `test/card-defaults.behavior.test.ts` (matches the project's per-feature behavior-test convention).
- **Exit state**: `npm run verify` green. Behavior tests assert on the persisted `card_property_values` row of a card created (a) with an explicit value overriding the default, (b) with no explicit value taking the default, (c) with a `(current user)` default resolving to the creating actor's id, and (d) on rejection of a default naming a value the property does not manage. `setCardDefaults` has its own persistence test (re-query the `card_defaults` table, not the command's return value).
- **Status**: DONE (2026-08-29) — exit criteria met: `test/card-defaults.behavior.test.ts` (7 tests) asserts on `card_defaults`, `card_property_values`, `card_versions` and `domain_events` for (a) an API-set explicit value overriding the default in its own version, (b) a bare `createCard` taking every default, (c) `(current user)` resolving to each actor's id, (d) rejection of an unmanaged enumerated value, a non-member user, a formula property, an unknown property and a full-member actor with nothing written, plus the settings page's `cardDefaults` intent and loader; `npm run verify` green (55 files, 1174 tests). Decisions taken in-phase: a defaulted card is **version 1** with the defaults in its snapshot (reviewer's question — legacy applied defaults before the first save), written by a new `insertInitialPropertyValues` primitive in `properties.server.ts` so that module stays the only `card_property_values` writer; a default on a transition-only property is honored at creation (a creation-time write never meets ADR-0009's guard, which sits in `setCardPropertyValue`); a stored default the property no longer accepts rejects the creation ("Unable to set default for …", legacy wording); `(current user)` stores the actor's id whether or not they are a member (legacy `User.current`); the set is replace-all per card type; legacy's default description and checklist items are not carried. Migration `0026_card_defaults.sql` generated by drizzle-kit and exercised by every real-DB suite.
